# Fleet & Assets Manager

نظام ويب متعدد المستخدمين لإدارة الأسطول والعتاد، مبني على معمارية معيارية
(Modular) بحيث تُضاف/تُعدّل الوحدات دون كسر بقية النظام.

## البنية

```
app/
├── core/           # النواة: إعدادات، أمان، صلاحيات، dependencies
├── database/       # اتصال قاعدة البيانات وتهيئتها فقط
├── shared/         # عناصر مشتركة عابرة للوحدات (mixins) - بدون منطق وحدة معينة
└── modules/        # كل وحدة مستقلة بذاتها:
    ├── users/          # المستخدمون، الأدوار، تسجيل الدخول
    ├── equipment/      # العتاد والسيارات
    └── dashboard/      # لوحة تحكم تجمّع مؤشرات من الوحدات الأخرى
        ├── models.py       # بيانات (SQLAlchemy)
        ├── schemas.py      # تحقق (Pydantic)
        ├── services.py     # منطق العمل
        ├── router.py       # الربط (FastAPI routes)
        └── templates/      # واجهة الوحدة (HTML خاص بها)

web/
├── main.py         # تشغيل وربط الراوترز فقط - بدون منطق عمل
└── templates/       # base.html المشترك بين كل الوحدات

static/             # CSS / JS / صور
```

## القاعدة المعمارية

- **كل وحدة تحت `modules/<name>/` تحتوي طبقاتها الأربع كاملة** (models,
  schemas, services, router) بدل تفريقها في مجلدات عامة. هذا يسمح بحذف أو
  تعطيل وحدة كاملة دون البحث في أماكن متفرقة.
- **الربط بين الوحدات يمر عبر services، لا عبر استيراد models مباشرة** قدر
  الإمكان، لتقليل الترابط (coupling).
- **إضافة وحدة جديدة** = مجلد جديد بنفس النمط + تسجيل الموديل في
  `database/init_db.py` + تسجيل الراوتر في `web/main.py`. لا تعديل على أي
  وحدة قائمة.

## التشغيل محليًا


# سجل تطوير الصيانة (Maintenance Development Log)

> هذا القسم يوثّق كل ما تم إنجازه بوحدتي **الصيانة** و**العتاد** المرتبطة بها.
> اقرأه كاملًا قبل أي تعديل جديد — التطوير مرّ بعدة مراحل وتصحيحات متتالية.

## أولًا: وحدة العتاد (Equipment) — التعديلات المنجزة ✅

- **الرقم الداخلي (`asset_code`)** لم يعد يُدخل يدويًا. يتولّد تلقائيًا:
  - `EQ-{رقم_التسجيل}` إن وُجد رقم تسجيل (مثال: `EQ-jcx`)
  - `EQ-TMP-{تسلسل}` إن لم يوجد
  - المنطق: `app/modules/equipment/services.py` → `generate_asset_code()`
- **`equipment_types.measurement_unit`** حقل إجباري (`"km"` أو `"hours"`) حل محل
  الحقل القديم `has_hour_meter` (Boolean). كل نوع عتاد يحدد وحدة قياسه عند
  الإنشاء، وفورم إضافة العتاد يُظهر الحقل المناسب فقط.
- **صفحة تفاصيل عتاد فردي** (`equipment_detail.html`) — تُفتح بالضغط على عتاد
  من صفحة `/equipment`، تعرض كل بياناته بما فيها العداد المناسب لنوعه. ✅ تم
  اختبارها وتعمل.
- **تحسينات إضافية على `/equipment`**: بحث، فلاتر (نوع/وضعية/حالة فنية)،
  إخفاء/إظهار أعمدة (محفوظ بـ localStorage)، عداد نتائج.

## ثانيًا: وحدة الصيانة (Maintenance) — مكتملة جزئيًا 🟡

### الموديلات (`app/modules/maintenance/models.py`):
- **`MaintenanceType`** — أنواع الصيانة (تغيير زيت، فحص فرامل...)
- **`MaintenanceSchedule`** — بند/خطة صيانة دوري، مرتبط بـ `equipment_type_id`
  (يُطبَّق على كل طرازات هذا النوع). فيه `interval_km`/`interval_hours`/
  `interval_days`، `internal_code` يتولّد تلقائيًا، `makes_equipment_unavailable`
- **`MaintenanceRecord`** — سجل تنفيذ فعلي (بلاغ عطل أو تنفيذ خطة مبرمجة)
- **`MeterReading`** — سجل تاريخي لقراءات العداد

### الصفحات الحالية:
| الرابط | الوصف | الحالة |
|---|---|---|
| `/maintenance` | رئيسية — 5 بطاقات + إشعارات مستحقة | ✅ |
| `/maintenance/periodic` | أوامر صيانة مفتوحة (قائمة بسيطة) | ✅ |
| `/maintenance/repairs` `/depot-day` `/annual-plan` `/inspections` | صفحات مؤقتة "قيد التطوير" | ⏳ |
| `/maintenance/settings` | إضافة أنواع/خطط صيانة (Admin) | ✅ لكن الشكل سيتغيّر — راجع "المطلوب لاحقًا" |
| `/maintenance/{id}/due` | صيانات مستحقة لعتاد معيّن | ✅ |

### وحدة الإشعارات المركزية (`app/modules/notifications/`):
تصميم Provider Pattern — كل وحدة تسجّل `register_provider()` تولّد إشعارات
بالشكل الموحّد `{key, source, severity, title, url}`. `get_all_notifications()`
تجمع من الكل، تمنع التكرار، ترتب حسب `severity` (`overdue` أحمر، `upcoming`
برتقالي). الهدف: أي وحدة مستقبلية (fuel، drivers...) تنضم تلقائيًا بدون
تعديل صفحة `/maintenance` الرئيسية.

### تصحيح مهم مُطبَّق:
`complete_maintenance_record()` بملف `services.py` كانت تستخدم الحقل القديم
`has_hour_meter` — صُحّحت لاستخدام `measurement_unit == "hours"`.

## ثالثًا: المطلوب لاحقًا 🔴 — إعادة تصميم إعدادات الصيانة

**القرار المتفق عليه:**
مرجع بصري: صورة "جدول الصيانة الدورية" (بنود بالصفوف، فترات بالأعمدة، ✓ عند
التقاطع). **هذا الجدول للعرض فقط** — حساب الاستحقاق الفعلي منطق منفصل
(`is_schedule_due()` بـ `maintenance/services.py`) يُستخدم بالإشعارات والصفحة
الرئيسية، وسيُطوَّر أكثر لاحقًا بشكل مستقل.

## دروس مستفادة (لتجنب تكرار الأخطاء)

1. النسخ اللصق من التيرمينال بالجوال غير موثوق (يتقطع/يعرض نسخ قديمة من
   الحافظة). الأفضل: `sed` على أرقام أسطر محددة (بعد `grep -n` للتأكد)، أو
   `cat > file << 'EOF'` لإعادة كتابة ملف كامل.
2. تحقق من توازن الأقواس `{}` بعد أي تعديل يدوي على JS داخل قوالب HTML —
   استخدم سكربت بايثون بسيط بدل القراءة البصرية.
3. شغّل `python3 -c "from app.modules.X import router"` قبل تشغيل السيرفر
   الكامل لكشف أخطاء الاستيراد بسرعة.
4. بعد أي تعديل على Models، احذف `fleet_assets.db` وأعد الإنشاء (بيئة تطوير،
   بيانات تجريبية) بدل migration يدوي معقّد.
5. قبل أي قرار تصميمي جوهري، اسأل: البيانات الحالية تجريبية أو مهمة؟
